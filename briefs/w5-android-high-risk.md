## title

Android emulator smoke: a high-risk request confirmed on a phone without biometric enrolment must show the refusal, and the runner must surface WebView errors

## evidence

`android.yml` run 39952987240 on commit 82a6295 (ubuntu runner, API 30-class x86_64 emulator, no biometric enrolment): the raw-CDP attach works (`PASS: attached to the WebView page http://tauri.localhost/`), `PASS: pairing by code` and `PASS: approve a request (signed)` pass. Scenario 3 fails: after clicking the `Confirm` button on the `m-request` card that contains `m-request-high`, `getByTestId("m-request-error")` never becomes visible in 180 s (`matches: 0, visible: 0`). The scenario is `apps/mobile/e2e/run.mjs` around lines 346-357 (it then asserts the error text names the biometric step and that no `/requests/req_cap/answer` call left the phone). The fake state service in `apps/mobile/e2e` serves `req_cap` as the high-risk request. The job log shows no page console output at all, so the cause is invisible.

## brief

Find why the real-device path shows no refusal and fix it at the root. The screen is `apps/ui/src/mobile/screens/InboxScreen.tsx` (unit tests `apps/ui/test/mobile-inbox.test.tsx`, browser spec `apps/ui/e2e/mobile-inbox.spec.ts`); the Android biometric step goes through `tauri-plugin-biometric` v2.4.0 (find the adapter in `apps/ui` or `apps/mobile` that wraps it, the Rust registration in `apps/mobile/src-tauri`, and the capability file under `apps/mobile/src-tauri/capabilities` that must allow `biometric:allow-status` and `biometric:allow-authenticate`). You cannot run the emulator here; reason from the code and reproduce in unit tests. Candidates to rule in or out, each with a test: (1) `checkStatus()` on an emulator without enrolment resolves `{ isAvailable: false, biometryType: 0, error, errorCode }` or rejects, in a shape the adapter does not map to the refusal; (2) `authenticate()` rejects with the plugin's error object or string and the screen's catch does not set the error state (or throws before it); (3) the call never settles (no prompt possible), so the screen waits forever: a bounded wait must end in the refusal; (4) the refusal is rendered without the `m-request-error` test id, or the card is re-rendered or removed first; (5) the plugin is not registered or not permitted in the debug build, so `invoke` rejects with a permission error that is swallowed. Drive `InboxScreen` with a biometric port that behaves like each case and assert the error with the word "biometric" appears and no answer is sent. Keep the existing happy path (enrolled, prompt passes, answer signed with the assertion) green. Change `apps/mobile/e2e/run.mjs` only where its expectation is wrong, and say why. Second part, regardless of the cause: make the emulator runner forward WebView console messages and uncaught exceptions to its own stdout over the CDP session it already holds (`Runtime.enable`, `Runtime.consoleAPICalled`, `Runtime.exceptionThrown`, prefixed `webview:`), with a unit test in `apps/mobile/e2e/cdp.test.ts`, so the next run shows the cause when something else fails. Docs: the mobile section of `docs/maintainers/apps.md` (and the testing doc if the runner's behaviour is described there); the Android rows in `docs/status/BLOCKERS.md` and the requirement rows R.5 and V.3 only if their status changes.

## hints

Run the UI tests with `pnpm --filter @forerunner/ui test` (or the vitest invocation the package.json names) and the mobile e2e unit tests with `pnpm --filter @forerunner/mobile exec vitest run e2e/cdp.test.ts`; `cargo check` in `apps/mobile/src-tauri` needs the Android targets and may not work on this runner: do not spend turns on it, reason from the Rust source instead.
