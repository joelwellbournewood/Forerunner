ITEM w4-desktop-confirm: P1: a high-risk change confirmed from the desktop app is performed on a solo install
  Requirement rows: J.3, J.4, Q.4 to Q.6 (confirmation rules), K.x; triage P1
  What is missing today (from docs/status/BLOCKERS.md and the handover), verbatim:
  Triage P1: a high-risk confirmation from the desktop sends `installId` as the device id; the daemon accepts it only once the desktop registers as a device. Verified end to end: `apps/ui/src/pages/SettingsPage.tsx:225` sends `deviceId: installId ?? 'desktop'` (the shell's install id, `inject.rs:74`); `server.ts:1081-1096` passes it through; `packages/commands/src/executor.ts:283` does `store.device.get(deviceId)` and `confirmation.ts:55` throws `approval_required: 'unknown device; pair it first'` when there is no row. The daemon's own desktop row (`registerDesktopDevice`, compose.ts:1976) has a store-generated id and exists only when `remoteCommandsEnabled` (compose.ts:418-430: false on a `sqlite:` store). So on every solo install each high-risk change from the desktop app is refused (monthly cap `budget.set`, `autonomy.set`, `email_mode_set`, capability enable/disable, device revoke, high-risk `request.answer`) and on a shared store the id never matches. Only the fake daemon accepts any id (`apps/ui/test/fake-daemon.ts:1733`), which is why `settings.test.tsx` passes; the daemon test (`loop-commands.test.ts:565`) confirms with a hand-registered `pc.id` the UI never sees. Proposed fix: register the desktop device row unconditionally (it needs no shared store), expose its id on `GET /me` (`server.ts:428`) and have `SettingsPage`/`ChangeCardDialog` send it; alternatively map the shell's `installId` to `rt.remote.device.id` on the daemon-token-authenticated confirm route. Tests: `packages/runtime/test/loop-routes.test.ts` (composed daemon on a sqlite store, high-risk command, `POST /commands/:id/confirm {answer:'device', deviceId:<id from /me>}` performs, a foreign id still refused), `apps/ui/test/settings.test.tsx` posts the `/me` id and the fake daemon refuses an unknown id like the real one. Note: the machine is shared with other builders; a test that fails only on a timeout under load is re-run once before it is treated as real.

  Read the files and lines named. Keep the security-command-actor and security-commands tests green (a web or runner device still needs the second factor). Also make the fake daemon in apps/ui/test refuse an unknown device id like the real executor and update every UI test that relied on the permissive fake.
