  Triage P0: `composeRuntime` attaches an install to the store's first human. Verified `packages/runtime/src/daemon/compose.ts:835-847`: `store.human.list(undefined, { limit: 1 })`, `humans[0] ?? insert(...)`; `ComposeOptions.identity` (line 245) only names a human to create. ADR 0024 ('Runtimes talk to Postgres directly; paired mode, PC online: it works on Postgres directly') and architecture.md make each PC's daemon a direct client of the shared Postgres; the cloud runner has a selector (`services/cloud-runner/src/config.ts:150 FORERUNNER_RUNNER_HUMAN`, `runner.ts:335 resolveHuman`), the daemon has none, so the second PC's daemon becomes the first human: runs that human's agent with its own vault keys, answers requests as them (`by = rt.human.id`, `server.ts:1083`), spends their cap, reads their inbox. Cross-human access in the spec's default two-person mode. testing.md says the scenario world 'assembles the composition by hand' for this reason, so no test covers two installs through `composeRuntime`. Proposed fix: a `humanId`/`humanEmail` selector (`config.json` written by `fr setup --human-name/--email`, env `FORERUNNER_HUMAN`), resolved like the runner's `resolveHuman`; on a non-sqlite store holding more than one human and no selector refuse to start with `ForerunnerError('identity_ambiguous')`. Test `packages/runtime/test/compose-identity.test.ts`: two humans in one store -> two compositions each bound to its own human and agent; two humans and no selector -> refused; single-human sqlite unchanged. Note: the machine is shared with other builders; a test that fails only on a timeout under load is re-run once before it is treated as real.
