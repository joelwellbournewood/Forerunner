# Test bench: the real daemon and the real UI, with a stand-in model

- **Start** (one bench per name; ports and name are yours): `node scripts/bench/start.mjs --name <n> --daemon-port <p> --ui-port <u> [--fresh] [--provider bench|fake|bench-live|none] [--env KEY=VAL ...]`. Home: `/tmp/frbench/<n>/home` (`--home` to change); `/tmp/frbench/<n>/bench.json` has `daemonUrl, uiUrl, home, token, pids, projectsRoot, modelCallLog, logs`.
- **A stand-in for GitHub** (`--githost <port>`): the fake git host of `testenv/src/githost` on that port (`githost-server.ts`, log in `<bench>/githost.log`), with the user `bench`, a classic token and two repositories: `bench/empty` (no commit, as one just created on GitHub) and `bench/seeded` (a README on `main`). Its token is stored in the home's vault and its URL as the GitHub API base with the app's own `fr setup --non-interactive` (`<bench>/setup-githost.log`), so Settings shows GitHub connected and a project created with the repository `bench/empty` or `bench/seeded` runs the whole branch, pull request and docs flow; `bench.json` has `githost: { url, repos }`; the repositories are bare ones under `<bench>/githost/bench/`, readable with `git --git-dir`. Stop ends it too. First used on 2026-11-02 for the github-result walk (an empty repository, the status PR, PRs waiting for the person).
- **Stop**: `node scripts/bench/stop.mjs --name <n>` (asks the daemon to quit, then ends exactly the recorded process groups). **Restart only the daemon**: `node scripts/bench/restart-daemon.mjs --name <n> [--hard] [--env KEY=VAL]` (`--hard` = crash; `--env KEY=` clears a value; the daemon gets a new token: call `reconnect(page, n)`).
- **Drive the UI** from a Playwright script anywhere: `const R = require("<repo>/scripts/bench/recorder.cjs")`; `const { browser, page } = await R.openApp(n)` (persistent profile, `{ freshProfile: true }` to wipe it; on a home whose setup was never finished every screen is the setup assistant: `await R.skipSetup(page)` presses "Set up later"); `await R.step(page, "label")` saves `steps/NN-label.png` + `.txt` and returns the visible text; console errors, failed requests and HTTP >= 400 go to `steps/problems.jsonl`.
- **Daemon API**: `await R.api(n, "GET", "/projects")` (throws `BenchApiError` at >= 400; `apiRaw` returns `{status, body}`). Setup not under test: `R.createPlannedProject(n, { project, goal, brief })`, `R.startSession(n, projectId)`, `R.waitForSession(n, id)`, `R.workspaceOf(n, projectId)`. Inspection: `R.modelCalls(n, role?)`, `R.daemonLog(n, lines)`, `R.problems(n)`, `R.until(fn, ms)`.
- **Model-call log**: `<home>/bench/model-calls.jsonl`, one line per request: `role` (intake, specialist, critic, chat, unknown), `label`, `model`, `effort`, `system`, `messages`, `tools`, `reply` (with `usage`), `injected`, and `usd` with the `price` row it was computed from (the app's own table: `packages/billing/src/pricing.ts` plus `<config>/pricing.json`; `usd: null` and `priceError` for a model without a row, such as the stand-in's `fake-*` rungs). It shows exactly what the app gives the model. No part of a key reaches it: the key is replaced whole and in any run of 8 or more of its characters, whatever the API echoes.
- **What it cost**: `node scripts/bench/calls.mjs --name <n> [--cap <usd>] [--json]` (or `--log <file>`) prints the calls and USD by kind (intake, specialist, critic, chat) and the calls without a price; with `--cap` it says what is left, and exits 3 once the total reaches the cap.
- **Project folder** (a project without a repository): `<home>/data/projects/<project id>/workspace` (the specialists' files, the docs, a local git repo).
- **Stand-in model** (`--provider bench`, `testenv/src/bench/`): plans 4-5 tasks for a brief (a web brief: index.html, script.js, styles.css, a check, README; any other brief: scope, src/main.js, a test, README), or 2 when the request says "Plan size: small" (a project whose brief is under 200 characters, at most two lines, no list and no repository: build, check, no risk tier named, so the critic reviews both; docs README.md and the decision only), specialists call the app's real tools (`list_dir`, `read_file`, `write_file`, `run_command`, `ask_person`), the critic reads the first changed file (`read_file` on the task's folder, ADR 0104) and accepts through `submit_review`, a page links only the stylesheet and script that exist or are written in the same run (it is tried in a headless browser), the chat replies `[stand-in model] I was given ...` (what context it got). Chat `tool: <name> {json}` calls that command tool; `tools?` lists them. Everything it writes says `[stand-in model]`: it proves mechanics, never model quality.
- **Failure injection** (`--env`, read at daemon start; substrings of a task title, comma-separated):
  - `FORERUNNER_BENCH_FAIL=<s>`: the specialist reports it could not do the work (`FORERUNNER_BENCH_FAIL_MODE=error`: the model call fails instead); every run, or the first `FORERUNNER_BENCH_FAIL_TIMES=<n>`.
  - `FORERUNNER_BENCH_CRITIC_REJECT=<s>`: the critic asks for rework on the first review (`FORERUNNER_BENCH_CRITIC_REJECT_TIMES=<n>|always`).
  - `FORERUNNER_BENCH_ASK=<s>`: the specialist asks the person (`ask_person` -> Inbox questions); after the answers it does the work.
  - `FORERUNNER_BENCH_MISSING=<s>`: an input the task needs is missing (the live "Members chart" of 2026-11-01): the specialist makes no deliverable, writes `notes/<task>.md` saying so and ends its report with "Questions for the person:" asking for the `data/...` file its brief names; the stand-in critic accepts it, as the live critic did. With `FORERUNNER_BENCH_ASK` on the same task it asks first, then does this after the answers (or Go ahead without).
  - `FORERUNNER_BENCH_INTAKE=malformed|error`: planning fails (every call, so the intake's one retry fails too: "Claude's plan could not be read. Forerunner asked Claude twice."). `FORERUNNER_BENCH_INTAKE_BAD=reason-too-long|fenced-docs|missing-tasks|not-json|too-big`: the first reply of each draft is one the live model sent (a 750-character `plan.reason`, docs holding code fences, a milestone without tasks, prose, the full 4-5 task plan when "Plan size: small" was asked); the intake reads the first two as they are (the reason shortened) and asks once more for the other three (`too-big` only for a draft from a short brief, with the plan's size in words), and the retry (its request carries the refused reply) gets the plan. `FORERUNNER_BENCH_PLAN=chain`: 7 tasks in a chain. `FORERUNNER_BENCH_PERSON=1`: adds a question task for the person. `FORERUNNER_BENCH_RISK2=<s>`: those tasks get risk tier 2 (they wait for Docker). `FORERUNNER_BENCH_DELAY_MS=<ms>` (default 250): wait per reply (not for the critic). `FORERUNNER_BENCH_CRITIC_DELAY_MS=<ms>` (default 0): wait per critic reply, so a task can be stopped or cancelled while it reads "Being reviewed" (leave it at 0 when the monthly calibration may run: some 160 critic calls).
- **Live mode** `--provider bench-live` (needs `ANTHROPIC_API_KEY`, or `FORERUNNER_ANTHROPIC_KEY`; kept out of the log): the real Messages API with the same log, first run on 2026-11-01 (bench `live1`). Without a key `start.mjs` refuses at once and starts nothing. With one it first stores the key in the home's vault the way an install gets it (`fr setup --non-interactive`, which checks it with Anthropic; a refused key ends the start with setup's reason, in `<bench>/setup.log`), so the setup assistant and Settings show Claude connected as on a real install. `bench.json` says `"live": true`. A dry run that spends nothing: point it at a local stand-in of the Messages API with `--env FORERUNNER_BENCH_LIVE_API=http://127.0.0.1:<port>` (any key-shaped value in `ANTHROPIC_API_KEY`); the daemon's calls and `fr setup`'s key check both go there (`setupEnv`; `FORERUNNER_ANTHROPIC_API` in `--env` names setup's base on its own). The stand-in must answer `GET /v1/models` and stream `POST /v1/messages`. Every bench's vault is a file in its home (`FORERUNNER_VAULT_BACKEND=file`), never the OS keyring. A daemon that exits during its start ends the start at once with its log. `--provider none`: what an install without a key does.
- **Intake journey**: `node scripts/bench/journeys/intake.cjs <n> [--brief "..."] [--goal "..."] [--project "..."] [--watch]`: New project with a one-line brief and no Goal, the plan card (tasks, who, cost, Needs Docker, the decision line), Approve and start; Try again at most twice when planning fails. `--watch` then waits (up to 20 minutes) for the session Approve and start began and checks that the critic reviewed every task an agent finished. Checks, the card's lines, the reviews and each intake call (the Plan size line, what the second call was told, output tokens) in `steps/intake-result.json`. It reads only what a person reads, so it runs on `--provider bench-live` too.
- **Smoke journey**: `node scripts/bench/journeys/smoke.cjs <n> [--live]` on a `--fresh` bench; result in `steps/smoke-result.json` (with `cost`: calls and USD by kind). It approves the plan card with **Approve and start**, which writes the tasks and starts a session at once (design §3.3), watches that session, and presses Start only while a session has a task to run (`runnableTasks`: ready or running, not waiting on the person, on Docker or on such a task), whether or not a task is done; a Start the dialog keeps disabled is a finding with the dialog's reason, and the journey goes on to its files and chat checks. Its checks look at structure and states, never at the stand-in's titles, file names or texts (`journeys/smoke-checks.cjs`): a plan card that says N ≥ 1 tasks and names every task it writes, Approve and start, a session that ends, files written (an .html page with a stylesheet and a script, whatever their names, in their own files or inline; a link to a file that was not written fails), a chat reply that is not empty, names a task and shows no `**`; "every planned task is done" fails on 0 of 0, and "every task the agents can do is done" allows the rest to wait on the person or Docker. When the project says planning failed it asks the chat about it (it must say so and point to Try again), then presses **Try again** up to twice (each try read only after its POST is answered, from the daemon first); each failure is a finding with what the project page said. Live mode (`bench.json` `live`, or `--live`) waits longer and expects the key saved on the setup's Claude step and a Done step that says Claude is connected. It also checks that the Overview shows the project's folder and the Files tab lists the page the work wrote, and that the critic reviewed the work (critic calls in the model-call log). It passes 100% on `--provider bench`; with `--env FORERUNNER_BENCH_INTAKE=malformed` it walks the planning-failed path, and with `--env "FORERUNNER_BENCH_ASK=page skeleton"` the path where every task waits on the person (no Start pressed after the first session; the checks on done work, files and the page fail as they should, the chat checks run).
- Rules: never kill by name pattern; one bench per agent; stop it when done. The monthly critic calibration runs as the critic agent, never on the day an install first sees its schedule and not without a model, so it no longer holds the person's agent on the 1st.
