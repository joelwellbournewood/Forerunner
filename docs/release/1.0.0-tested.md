# What 1.0.0 is tested on

Forerunner 1.0.0 was released on 2026-10-26 with known gaps. The human decided to release
with them. This page says, area by area, what was tested and how.

There are three kinds of evidence:

- **Live.** Real hardware, real accounts, real models. The strongest evidence.
- **Stand-in.** Our own tests against things we built to imitate the real ones: the fake model
  provider, the in-process test mail server, the fake git host, the in-process state service,
  the hosted Android emulator, fake speech engines. These are useful. They are weaker evidence.
  On 2026-10-26 real runs found bugs that stand-in tests had not caught (see
  [Bugs the stand-ins missed](#bugs-the-stand-ins-missed)).
- **Not tested.** No run of any kind on the real thing.

Every claim below names its source: a run ID, a CI run, a commit or a date. The sources are
[gates.md](../status/gates.md), [requirements.md](../requirements.md),
[BLOCKERS.md](../status/BLOCKERS.md) and [PROGRESS.md](../status/PROGRESS.md). A few facts
from 2026-10-26 were reported by the human after their runs and are not yet in those files.
They are marked "(reported 2026-10-26)".

  failure was a harness defect in the subscription file, fixed in 7b150f8 and a4a84f5; that file

  source checkout, not from the MSI.

**Built and published, not run.**

- The MSI, by `release.yml` run 40395549204 (rc.4).

**Tested only against stand-ins.**

- CI on `windows-latest` runs lint, types, unit tests, the Postgres integration tests, the nine
  scenarios and the phase 3, 4, 5 and 7 gate harnesses on the fake provider. Last green on
  ef18b5a (CI run 40360382369, 2026-10-26).
- The scripted fresh install from source took 494 s on a fresh `windows-latest` runner
  (run 40195327081, 2026-10-25). The target is 15 minutes.

**Not tested.**

- Installing the published MSI and running the installed app. gates.md has no record of it.
- The live suite on rc.4's code. It last ran on a76e259.
- Windows-only shell code beyond CI's `windows-latest` (CHANGELOG known issue [21]).

**Known issues.**

## Android app

**Tested live.**

- R.1 on a real phone, a Samsung SM-S911B. On 2026-10-26 01:31 local the rc.3 APK installed
  and launched to its pairing screen. Its SHA-256 matched the signed manifest. On 2026-10-26
  22:02 local rc.4 installed over rc.3 as an update with the same signing key and launched
  (`R1 RESULT: PASS v1.0.0-rc.4`). Source: gates.md, "Release 1.0 criteria".
- `release.yml` checked the APK's signature with `apksigner`. The PC did not.

**Tested only against stand-ins.**

- The emulator smoke on the hosted API 30 emulator passed five times in a row on
  2026-10-25 (`android.yml` runs 40182115934, 40183122342, 40185240435, 40195655038,
  40198266359), the last on a76e259. It has not run on rc.4. It drives the real WebView:
  pairing by code, a signed approval, the high-risk card refused without a biometric, Reviews,
  Upload, the voice turn, scenario 9 and its Undo.
- The phase 5 phone harness and scenario 9 use the app's own code against the real state
  service routes, on the fake provider.

**Not tested.**

- Pairing a real phone with a real PC and state service.
- Approving a request, or a high-risk card with a real fingerprint, on a real phone.
- Push notifications on any device (see [Push notifications](#push-notifications)).

**Known issues.**

- rc.3, rc.4 and 1.0.0 all carry versionCode 1000000, because the code ignores the
  pre-release part of the version. Android may not offer 1.0.0 as an update over an rc.
  Uninstall the rc first.
- On rc.3 the app's header sat under the phone's status bar (the R.1 screenshot). ee056ae
  pads the WebView below the status bar and above the navigation bar. The fix is not confirmed
  on the phone.
- The emulator image's WebView (Chrome 83) renders the app unstyled. A phone needs a current
  Android System WebView.
- Push-to-talk on the phone relays the typed line. The phone's own speech engine speaks the
  reply.

## Voice

**Tested live.**

- Windows, NVIDIA RTX 3060, GPU profile. Works end to end: speech in, the reply streamed as
  text, speech out, barge-in (pressing Talk interrupts) and text-only replies.
- Heard first audio (from releasing push-to-talk to the first sound from the speaker), D.8:
  - Morning of 2026-10-26 (10:33Z, head 7293a41): median 1383 ms, p90 1998 ms over 4 counted
    turns. Not counted: text-mode turns, three turns interrupted before first audio, and the
    first turn, lost to a speech-recognition crash. Stage medians: transcript 149 ms, model
    first token 840 ms, first audio 327 ms (gates.md D.8).
  - Evening of 2026-10-26 (2c54f66): median 2139 ms, 4 turns (reported 2026-10-26).
  - The target is 1.2 s. **Not met.** The requirement asks for 10 turns; the human waived that.
- CPU profile on the same PC: median 4271 ms, p90 9320 ms (6 turns, 2026-10-26T00:53Z); median
  4010 ms, p90 7436 ms (7 turns, 2026-10-26T02:01Z). Paid model-watch evals were loading the
  CPU during the second run (gates.md D.8).

**Tested only against stand-ins.**

- The phase 5 gate and scenario 3 run the real voice loop with fake speech engines on a
  simulated clock: median 520 ms over 29 turns. This proves the loop's accounting, not real
  speed (gates.md phase 5).
- The speech-recognition helper's crash and retry paths, against crashing stand-in helpers
  (`packages/voice/test/local-helpers.test.ts`).

**Not tested.**

- Voice on Linux.
- Cloud voice providers (Deepgram, Cartesia, ElevenLabs). No keys were provided.
- Open mic. Every live turn was push-to-talk.

**Known issues.**

- First audio misses 1.2 s. The model's first token is the largest stage.
- The speech-recognition helper crashed with 0xC0000005 (access violation) on Windows on the
  first utterance of the morning GPU run. The cause is not proven. The evening GPU run
  (2c54f66) had no crash. The helper now restarts, retries the utterance once with a different
  decode, and logs a traceback (CHANGELOG rc.4).
- On the measured PC the CPU profile was two to three times slower than the GPU profile
  (medians about 4.0 s against 1.4 and 2.1 s).
- The voice panel's heard-first-audio figure can read slightly low for hotkey turns.

## Bugs the stand-ins missed

Real runs on 2026-10-26 found these bugs. Stand-in tests had passed over them.

1. **Git sent the token as a bearer header.** The fake git host accepted it. GitHub's git
   endpoint needs Basic authentication. Found by the V.8 live run. 1.0.0 includes the fix
   (merged before the tag); its live re-run is pending.
2. **Paid model-watch evaluations on fresh installs.** Fresh test installs started paid
   evaluations without asking. About USD 13 was spent across those installs (reported
   2026-10-26). Fixed by the consent rules of ADR 0089 in rc.4.
3. **Android version and layout on a real phone.** rc.3 and rc.4 carry the same versionCode
   (1000000), so a later build may not be offered as an update. On rc.3 the header sat under
   the status bar. Neither showed in the emulator smoke. The header fix (ee056ae) is not confirmed
   on the phone; the versionCode is unchanged.

A pass against a stand-in shows the logic is right against our model of the real thing. It
does not show the real thing behaves like our model. Read every "stand-in" line above with
that in mind.
