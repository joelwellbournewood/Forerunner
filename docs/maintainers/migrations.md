# Migrations

Schema migrations for the state store (`packages/state`) and, later, memory-format
migrations for lesson files (`packages/memory`). The schema itself is documented in the
generated [data-model.md](data-model.md).

## Purpose

One declarative schema (`packages/state/src/schema.ts`) drives two SQL dialects. Migrations
exist so a running install, a shared Postgres state service and a fresh test database all
reach the same schema version by the same path, and so the shipped v1 can never drift
silently: migration v1 is a *snapshot* of the generator, and a test fails the moment the
schema and the snapshot disagree.

## How it works

- `src/migrations/types.ts`: `Migration = { version, name, up: { sqlite: string[]; postgres: string[] } }`.
  Versions are contiguous from 1. There is no `down`: a rollback is a new forward migration.
- `src/migrations/0001-initial.ts`: generated by `scripts/write-initial-migration.ts` from
  `generateInitialMigration()` (tables in dependency order, indexes, append-only triggers).
  Never edited by hand. `test/schema.test.ts` asserts it equals the generator output.
- `src/migrations/0002-headroom-savings.ts`: `run.context_transforms`, `run.headroom_used`,
  `session.headroom_saved_tokens` (ADR 0003).
- `src/migrations/0003-sources.ts` (spec A.4, ADR 0056): `source.kind` gains `github_repo`
  and the `source_candidate` table arrives with its three indexes. The enum change is the
  copy-table dance on SQLite (`source_v3` created with the new CHECK, rows copied column by
  column, the old table dropped, the new one renamed, the unique `(kind, locator)` index
  recreated; nothing referenced `source` before this migration) and a `DROP CONSTRAINT` /
  `ADD CONSTRAINT` pair on Postgres. The DDL is the generator's output written out and frozen.
- `src/migrations/0004-shared-secrets.ts` (spec S.13, ADR 0065): hand written and frozen:
  `device.wrap_public_key` (the install's X25519 wrapping key, nullable) and the
  `secret_grant` table with its two indexes; its DDL is the generator's output at the time
  of writing, pasted as literals so a later schema change cannot alter a shipped migration.
  It is v4, not v3, because the sources migration shipped first on the release branch.
- `src/migrations/index.ts`: `MIGRATIONS` (ascending) and `migrate(db, { clock?, migrations? })`.
  `migrate` creates `schema_migrations (version PK, name, applied_at)` if missing, then applies
  every pending migration inside **one transaction** (both dialects have transactional DDL) and
  records it with the Clock's time. On Postgres it first takes
  `pg_advisory_xact_lock(hashtext('forerunner_schema_migrations'))` so two processes starting at
  once serialise. A second call is a no-op (`{ applied: [], version }`).
- `openStore({ url })` runs `migrate` on open unless `migrate: false` is passed.
- The runtime's private memory index (`<data>/memory/private.sqlite`, ADR 0083) is a second
  SQLite opened through the same `openStore` (`sqlite: { foreignKeys: false }`), so it carries
  the full schema at the same version and a schema migration applies to it at the next start
  too; only its `lesson` table holds rows (the `agent_private` ones, which the Postgres adapter
  refuses with `MEMORY_SCOPE_VIOLATION`).
- Dialect differences live in `src/db/dialect.ts` (`sqlType`, `sqlLiteral`, `toPositional`,
  `jsonArrayContains`). Statements that are identical in both dialects (most DML, `RETURNING`,
  `ON CONFLICT`, `CHECK`, `CREATE INDEX IF NOT EXISTS`) are written once. Postgres >= 14 is
  required (`CREATE OR REPLACE TRIGGER`); SQLite is Node 22's bundled 3.50.
- Append-only tables (`event`, `audit_log`) get triggers that refuse UPDATE and DELETE. A new
  append-only table needs `appendOnly: true` in its `EntityDef`; the generator emits the
  triggers (SQLite: two `RAISE(ABORT)` triggers; Postgres: one shared `forerunner_append_only()`
  function plus a trigger per table).

## How to change it

### Adding a schema migration (v2 and later)

1. Edit `packages/state/src/schema.ts` (new table, column, index, enum value, check). Keep every
   column's one-line description; the doc is generated from it.
2. Run `pnpm vitest run --project unit --dir packages/state`. The snapshot test now fails: that is
   the signal that a migration is needed. Do **not** regenerate `0001-initial.ts`.
3. Create `packages/state/src/migrations/0002-<name>.ts` exporting `MIGRATION_0002` with the
   `up` statements for **both** dialects. Use the generator for whole tables
   (`createTableSql(ENTITIES.new_table, "sqlite")`, `createIndexSql`, `appendOnlySql`) and write
   `ALTER TABLE` by hand for columns. Mind the dialect differences:
   - SQLite `ALTER TABLE ... ADD COLUMN` cannot add a column with a non-constant default or a
     `REFERENCES` clause that would need validation; add it nullable, backfill with `UPDATE`,
     and enforce in code if needed.
   - Changing an enum means dropping and re-adding the named `CHECK` constraint. Postgres:
     `ALTER TABLE t DROP CONSTRAINT t_col_enum, ADD CONSTRAINT t_col_enum CHECK (...)`. SQLite
     cannot alter constraints: create the new table, copy, drop, rename (inside the migration's
     transaction).
   - Booleans are `INTEGER 0/1` in SQLite and `BOOLEAN` in Postgres; JSON is `TEXT` vs `JSONB`;
     integers and money are `INTEGER` vs `BIGINT`. `sqlLiteral()` renders defaults correctly.
4. Append the migration to `MIGRATIONS` in `src/migrations/index.ts`.
5. Update the snapshot test's expectation only if you added a *second* generator-driven
   baseline; otherwise leave it: v1 stays frozen and the test compares v1 with the generator's
   output for the **v1 subset**. In practice: when `generateInitialMigration()` no longer equals
   v1 because the schema grew, change the test to compare `generateSchemaSql()` against
   `v1 + your migration` applied to an empty database (see "Tests" below), and keep the
   assertion that `0001-initial.ts` is byte-stable.
6. Run `pnpm docs:schema` to regenerate `docs/maintainers/data-model.md`, and run the unit and
   integration tests (`FORERUNNER_TEST_PG=...`). The conformance suite applies every migration
   against an empty SQLite and an empty Postgres schema.
7. Spec M.6: both apps must be on a compatible schema version before sync resumes. The state
   service reports `schema_migrations.version`; a client whose `MIGRATIONS.length` is lower
   refuses to sync and asks for an update.

### Re-creating the v1 baseline

Only before v1 has shipped anywhere (no installed database, no shared service). Run
`pnpm exec tsx packages/state/scripts/write-initial-migration.ts`, then `pnpm docs:schema`.
After 1.0 this script is history: a new baseline would strand every installed database.

### Memory-format migrations (placeholder)

Lessons are Markdown files with YAML frontmatter (ADR 0002). When the frontmatter format
changes, `packages/memory` will carry a `memory_format` version in each file and a migrator
that rewrites files in place on first load, with a backup next to the memory root. Until that
package lands, the format is version 1 and nothing migrates. The procedure will mirror the
schema one: a numbered migration module, applied once, recorded in the store (`extension` row
of kind `skill` named `memory-format`), tested on fixture directories for both path styles.

## Tests

- `packages/state/test/schema.test.ts`: snapshot equality for both dialects (v1 frozen by
  hash; the generator's output minus the v2 columns, the v3 table and the v3 enum value,
  the v4 column and the v4 table equals v1), v1 + v2 + v3 + v4 applied equals the
  generator's schema (SQLite shape), a v1 database migrated forward (v2 defaults, v3 and v4
  applied in the same run) and a v2 database migrated forward twice over: `source` rows
  survive the rebuild with their version and unique index, `github_repo` accepted,
  candidates round-trip with the foreign key to their source; devices read back without a
  wrapping key and take one, secret grants can be filed, generator output shape (types, checks,
  FKs, indexes, triggers), `migrate` applies once and records with the clock, contiguity
  check, a failing statement rolls back the whole run, doc currency.
- `packages/state/test/suite.ts` (run by `sqlite.test.ts` and `postgres.integration.test.ts`):
  migrations idempotent, every table created, full round trips for every entity, and the
  repository behaviour on top of the migrated schema; its "keeps private rows out of the shared
  store" case asserts the `MEMORY_SCOPE_VIOLATION` refusal of an `agent_private` insert, update,
  patch and supersede on the Postgres adapter and the acceptance on SQLite.
- `packages/state/test/lesson-scope.test.ts`: the refusal on a Postgres-dialect handle that
  fails the test if a statement reaches it (so it is proven without a database), the SQLite
  acceptance, and a store opened with `sqlite: { foreignKeys: false }` holding a lesson whose
  agent and project rows live in another store (the private index).
- CI runs `pnpm docs:schema` and fails on a diff of `docs/maintainers/data-model.md`.

## Known issues

- A `lesson` migration that backfills from other tables (`agent`, `project`) finds them empty in
  the private memory index; write such a backfill so an empty join is a no-op.
- No `down` migrations by design; test a risky migration on a copy of the database first
  (`sqlite:` files can be copied; Postgres with `pg_dump`).
- SQLite cannot alter constraints in place; enum changes need the copy-table dance described
  above and are slow on very large `event` tables. The event table is append-only, so a future
  migration may archive old sessions first.
- `migrate` holds one transaction for all pending migrations. A very long backfill on Postgres
  blocks writers for its duration; split such work into a migration that adds the column and a
  background job that fills it.
